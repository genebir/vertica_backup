# v_dump — Vertica 逻辑备份工具 (client-side)

[🇰🇷 한국어](README.md) · [🇬🇧 English](README.en.md) · [🇯🇵 日本語](README.ja.md) · **🇨🇳 中文**

> 在无法触碰服务器的环境中，**仅凭网络连接（5433）** 就能对 Vertica 的数据、结构、存储过程
> 进行逻辑备份与恢复的工具。**为受限环境打造的 Vertica 版 `pg_dump`。**

数据以 `COPY` 兼容的 `.dat`（管道分隔）文件落地，结构以 DDL 落地。恢复只需
`vsql -f load.sql` 一行。完全不需要服务器文件系统、SSH 或管理员权限。

---

## 为何而生 — vbr 用不了的地方

Vertica 官方备份工具 **vbr** 以节点的 **文件系统 + SSH 访问**，以及节点可写的备份存储
为前提。然而当目标 Vertica **无卷地以 Docker 运行、且仅能通过客户端访问（5433）** 时，
vbr **根本无法运行**。

v_dump 正是为填补这一空隙而生 —— **仅凭一个只读 SQL 连接** 就能完成备份。

> 打个比方，它就如同 `pg_dump`。虽然比文件系统快照慢，但因其 **逻辑化、可移植、可选择性**，
> 全世界每天都在使用它。v_dump 在受限的 Vertica 环境中扮演的正是这个角色。

## v_dump vs vbr

| | **vbr（官方）** | **v_dump** |
|---|---|---|
| 方式 | 物理 —— 直接复制 ROS 文件 | 逻辑 —— `SELECT` → 文本 `.dat` + DDL |
| 访问要求 | 节点 **文件系统 + SSH** | 仅需 **网络（5433）只读账户** |
| 服务器足迹 | 在服务器上安装、运行 | **0**（仅在客户端） |
| 可移植性 | 绑定于相同/兼容的集群 | **任意 Vertica 皆可**（与版本、节点数无关） |
| 可选择性 | 可按对象粒度（较重） | 1 张表～整个模式，**自由选取** |
| 输出 | 不透明的物理文件 | **人类可读** 的文本 |
| 一致性 | 纪元快照（一致） | 逐表 SELECT（无时点一致性） |
| 增量 | 支持 | 无（每次全量） |
| 规模/速度 | 大数据量下压倒性优势（节点并行复制） | 由单一客户端拉取 → 慢 |

**二者并非竞争关系。** vbr 面向 *"拥有服务器的环境的全库灾难恢复"*，v_dump 面向 *"在无法
触碰服务器的环境中，仅凭网络完成的逻辑化、可选择、可移植的抽取"*。

### 何时用何者

- **用 v_dump** —— 无法访问服务器/节点（无卷的 Docker、被锁定的托管环境），需要逻辑化、
  可移植的转储，只要特定表/模式，生产→开发的数据迁移，仅凭客户端即可部署。
- **用 vbr** —— 可访问服务器，目标是超大规模全库备份、增量、时点一致的 DR。

## 优点

| 优点 | 内容 |
|---|---|
| **免权限** | 一个只读 SQL 连接。无需 SSH、节点访问、服务器权限 → 安全友好 |
| **多节点** | 在 `host` 中以逗号列出节点 → 自动 failover + 将并行分散到各节点 |
| **可移植性** | `.dat`+DDL 可加载到版本、拓扑不同的任意 Vertica |
| **可选择性** | 按 1 张表、多张表、模式粒度导出，仅恢复其中 1 张 |
| **透明性** | 打开 `.dat` 即可原样查看、验证内容 |
| **隔离网部署** | 一个镜像 + 一个捆绑包，目标服务器零安装（`docker`/`podman`） |
| **速度** | 自适应并行转储、恢复（自动），对巨型表做行分片 |
| **传输效率** | `--compress`（gzip）—— 大幅降低传输/保存容量，COPY 直接读取，无损 |
| **运维便利** | 进度条、幂等 DDL、自动包含存储过程、无损 escape |

## 工作原理

```
备份:  vertica-python ──SELECT──▶ 值 escape ──▶ <schema>.<table>.dat
       EXPORT_OBJECTS ──▶ schema.ddl.sql (+ 匹配的存储过程, 幂等型)
恢复:  vsql ──COPY ... FROM LOCAL──▶ Vertica
```

- **`.dat`** —— 直接采用 Vertica `COPY` 的默认约定（管道分隔、`\N` 表示 NULL、反斜杠 escape）→
  最快的再加载。换行、制表符、特殊字符 **无损** 往返。
- **自适应并行** —— 根据工作负载自动决定：琐碎则顺序执行，表多则按表并行，
  巨型表则按行分片。**转储与恢复两侧** 均并行。工作进程数为 `min(核心数, 4)`（可用 `V_DUMP_JOBS` 调整）。
- **压缩**（`--compress`）—— 将 `.dat` 以 gzip 压缩。减轻气隙传输的负担，恢复时通过 `COPY ... GZIP`
  直接读取压缩文件，**无损**。
- **幂等 DDL** —— 采用 `CREATE ... IF NOT EXISTS` / `OR REPLACE`，重复执行也安全。

## 快速开始

```bash
# [构建机, 有互联网] 一次性打包
./docker/package.sh                  # → v_dump-deploy.tar.gz (镜像+包装脚本+yaml+加载器)

# [目标主机, 隔离网] 解包并加载后即可使用
tar xzf v_dump-deploy.tar.gz && cd v_dump-deploy
./LOAD-ME.sh
./v_dump-docker.sh dump --schema YOUR_SCHEMA               # 备份
./v_dump-docker.sh restore YOUR_SCHEMA/all --with-ddl      # 恢复
```

## 局限（坦诚相告）

- **时点一致性** —— 由于逐表读取，若转储过程中数据发生变化，表之间可能不一致
  （与 vbr 的纪元快照不同）。
- **规模** —— 由于将所有行都由单一客户端拉取的结构，对超大规模全库从根本上较慢。
  那个领域应交给 vbr / `EXPORT TO`。
- **无增量** —— 每次备份都是全量抽取。

> 一旦获得服务器/容器的文件访问权限，便可扩展为基于 `EXPORT TO DELIMITED` 的高速路径
> （绕过逻辑抽取的天花板）。当前是以"仅有 5433 客户端访问"为前提的最优配置。
