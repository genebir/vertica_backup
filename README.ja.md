# v_dump — Vertica 論理バックアップツール (client-side)

[🇰🇷 한국어](README.md) · [🇬🇧 English](README.en.md) · **🇯🇵 日本語** · [🇨🇳 中文](README.zh.md)

> サーバーに触れられない環境で、**ネットワーク接続(5433)だけで** Vertica のデータ・構造・プロシージャを
> 論理的にバックアップ・復元するツール。**制約された環境のための Vertica 版 `pg_dump`。**

データは `COPY` 互換の `.dat`(パイプ区切り)ファイルへ、構造は DDL として出力する。復元は
`vsql -f load.sql` の一行。サーバーのファイルシステム・SSH・管理者権限はまったく不要だ。

---

## なぜ作ったか — vbr が使えない場所

Vertica 公式バックアップツール **vbr** は、ノードの **ファイルシステム + SSH アクセス**、そしてノードが
書き込めるバックアップストレージを前提とする。ところが対象の Vertica が **ボリュームなしで Docker で起動しており、
クライアントアクセス(5433)のみ可能**な場合、vbr は **実行そのものが不可能**だ。

v_dump はまさにその隙間のためのツールだ — **読み取り専用 SQL コネクション一つだけで**バックアップする。

> たとえるなら `pg_dump` と同じだ。ファイルシステムのスナップショットより遅いが、**論理的・移植可能・選択的**であるため、
> 世界中が毎日使っている。v_dump は制約された Vertica 環境におけるその役割を担う。

## v_dump vs vbr

| | **vbr (公式)** | **v_dump** |
|---|---|---|
| 方式 | 物理的 — ROS ファイルをそのままコピー | 論理的 — `SELECT` → テキスト `.dat` + DDL |
| アクセス要件 | ノード **ファイルシステム + SSH** | **ネットワーク(5433)読み取り専用アカウント**のみ |
| サーバーフットプリント | サーバーへインストール・実行 | **0** (クライアントのみ) |
| 移植性 | 同一/互換クラスタに縛られる | **どの Vertica へも** (バージョン・ノード数を問わず) |
| 選択性 | オブジェクト単位で可能(重い) | テーブル 1 個〜スキーマまで、**自由に** |
| 出力 | 不透明な物理ファイル | **人が読める**テキスト |
| 一貫性 | エポックスナップショット(整合) | テーブルごとの SELECT (時点整合なし) |
| 増分 | サポート | なし(毎回全量) |
| 規模/速度 | 大容量で圧倒的(ノード並列コピー) | 単一クライアントで引き込む → 遅い |

**競合関係ではない。** vbr は *「サーバーを所有する環境のフル DB 災害復旧」*、v_dump は *「サーバーに触れられない
環境でネットワークだけで行う論理的・選択的・移植可能な抽出」* だ。

### いつ何を

- **v_dump を使う** — サーバー/ノードアクセス不可(ボリュームなしの Docker、ロックされたマネージド)、論理的・移植可能な
  ダンプが必要、特定のテーブル/スキーマだけ、本番→開発のデータ移行、クライアントのみでのデプロイ。
- **vbr を使う** — サーバーアクセスが可能で、超大容量フル DB バックアップ・増分・時点整合 DR が目的。

## 利点

| 利点 | 内容 |
|---|---|
| **無権限** | 読み取り専用 SQL コネクション一つ。SSH・ノードアクセス・サーバー権限は不要 → セキュリティに優しい |
| **マルチノード** | `host` にノードをカンマで列挙 → 自動 failover + 並列をノードに分散 |
| **移植性** | `.dat`+DDL はバージョン・トポロジーの異なるどの Vertica へもロード可能 |
| **選択性** | テーブル 1 個・複数個・スキーマ単位で出力し、1 個だけ復元 |
| **透明性** | `.dat` を開いて中身をそのまま確認・検証 |
| **閉域網デプロイ** | イメージ一つ + バンドル一つ、対象サーバーへのインストール 0 (`docker`/`podman`) |
| **速度** | 適応型の並列ダンプ・復元(自動)、巨大テーブルの行シャーディング |
| **転送効率** | `--compress`(gzip) — 転送/保管容量を大幅に削減、COPY が直接読み込み無損失 |
| **運用の利便性** | 進捗バー、冪等 DDL、プロシージャの自動含有、無損失 escape |

## 動作原理

```
バックアップ:  vertica-python ──SELECT──▶ 値 escape ──▶ <schema>.<table>.dat
              EXPORT_OBJECTS ──▶ schema.ddl.sql (+ マッチするプロシージャ、冪等型)
復元:        vsql ──COPY ... FROM LOCAL──▶ Vertica
```

- **`.dat`** — Vertica `COPY` のデフォルト規約(パイプ区切り、`\N` NULL、バックスラッシュ escape)のまま →
  最速の再ロード。改行・タブ・特殊文字を **無損失**でラウンドトリップ。
- **適応型並列** — ワークロードを見て自動判定する: 細かければ順次、テーブルが多ければテーブル並列、
  巨大テーブルは行単位でシャーディング。**ダンプ・復元の両方**で並列。ワーカーは `min(コア数, 4)`(`V_DUMP_JOBS` で調整)。
- **圧縮**(`--compress`) — `.dat` を gzip で。エアギャップ転送の負担を減らし、復元は `COPY ... GZIP`
  で圧縮ファイルを直接読み込み **無損失**。
- **冪等 DDL** — `CREATE ... IF NOT EXISTS` / `OR REPLACE` なので再実行しても安全。

## クイックスタート

```bash
# [ビルドマシン、インターネットあり] 一度にパッケージング
./docker/package.sh                  # → v_dump-deploy.tar.gz (イメージ+ラッパー+yaml+ローダー)

# [対象ホスト、閉域網] 展開してロード後すぐに使用
tar xzf v_dump-deploy.tar.gz && cd v_dump-deploy
./LOAD-ME.sh
./v_dump-docker.sh dump --schema YOUR_SCHEMA               # バックアップ
./v_dump-docker.sh restore YOUR_SCHEMA/all --with-ddl      # 復元
```

## 限界 (正直に)

- **時点整合性** — テーブルを個別に読むため、ダンプ中にデータが変わるとテーブル間で不一致が起こりうる
  (vbr のエポックスナップショットとは異なる)。
- **規模** — すべての行を単一クライアントで引き込む構造のため、超大容量フル DB には根本的に遅い。
  その領域は vbr / `EXPORT TO` が適している。
- **増分なし** — 毎回のバックアップが全量抽出。

> サーバー/コンテナのファイルアクセスが確保できれば、`EXPORT TO DELIMITED` ベースの高速経路へ拡張できる
> (論理抽出の天井を回避)。現在は「5433 クライアントアクセスのみ」を前提とした最適構成だ。
