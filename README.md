# v_dump — Vertica 논리 백업 도구 (client-side)

**🇰🇷 한국어** · [🇬🇧 English](README.en.md) · [🇯🇵 日本語](README.ja.md) · [🇨🇳 中文](README.zh.md)

> 서버를 만질 수 없는 환경에서, **네트워크 연결(5433)만으로** Vertica의 데이터·구조·프로시저를
> 논리적으로 백업하고 복원하는 도구. **제약된 환경을 위한 Vertica용 `pg_dump`.**

데이터는 `COPY` 호환 `.dat`(파이프 구분) 파일로, 구조는 DDL로 떨어뜨린다. 복원은
`vsql -f load.sql` 한 줄. 서버 파일시스템·SSH·관리자 권한이 전혀 필요 없다.

---

## 왜 만들었나 — vbr 이 안 되는 곳

Vertica 공식 백업 도구 **vbr** 은 노드 **파일시스템 + SSH 접근**, 그리고 노드가 쓸 수 있는
백업 저장소를 전제로 한다. 그런데 대상 Vertica 가 **볼륨 없이 Docker 로 떠 있고 클라이언트
접근(5433)만 가능**하면 vbr 은 **실행 자체가 불가능**하다.

v_dump 는 바로 그 틈을 위한 도구다 — **읽기전용 SQL 커넥션 하나만으로** 백업한다.

> 비유하면 `pg_dump` 와 같다. 파일시스템 스냅샷보다 느리지만, **논리적·이식 가능·선택적**이라
> 전 세계가 매일 쓴다. v_dump 는 제약된 Vertica 환경의 그 자리다.

## v_dump vs vbr

| | **vbr (공식)** | **v_dump** |
|---|---|---|
| 방식 | 물리적 — ROS 파일을 그대로 복사 | 논리적 — `SELECT` → 텍스트 `.dat` + DDL |
| 접근 요건 | 노드 **파일시스템 + SSH** | **네트워크(5433) 읽기전용 계정**만 |
| 서버 발자국 | 서버에 설치·실행 | **0** (클라이언트에서만) |
| 이식성 | 같은/호환 클러스터에 묶임 | **어떤 Vertica로도** (버전·노드수 무관) |
| 선택성 | 객체 단위 가능(무거움) | 테이블 1개~스키마, **자유롭게** |
| 출력 | 불투명 물리 파일 | **사람이 읽는** 텍스트 |
| 일관성 | 에폭 스냅샷(정합) | 테이블별 SELECT (시점 정합 X) |
| 증분 | 지원 | 없음(매번 전량) |
| 규모/속도 | 대용량에 압도적(노드 병렬 복사) | 단일 클라이언트로 당김 → 느림 |

**경쟁 관계가 아니다.** vbr 은 *"서버를 소유한 환경의 풀DB 재해복구"*, v_dump 는 *"서버를 못
만지는 환경에서 네트워크만으로 하는 논리적·선택적·이식 가능한 추출"* 이다.

### 언제 무엇을

- **v_dump 를 쓴다** — 서버/노드 접근 불가(볼륨 없는 Docker, 잠긴 관리형), 논리·이식 가능한
  덤프가 필요, 특정 테이블/스키마만, 운영→개발 데이터 이관, 클라이언트만으로 배포.
- **vbr 을 쓴다** — 서버 접근이 되고, 초대용량 풀DB 백업·증분·시점정합 DR 이 목적.

## 장점

| 장점 | 내용 |
|---|---|
| **무권한** | 읽기전용 SQL 커넥션 하나. SSH·노드접근·서버권한 불필요 → 보안 친화 |
| **이식성** | `.dat`+DDL 은 버전·토폴로지 다른 어떤 Vertica 로도 적재 |
| **선택성** | 테이블 1개·여러 개·스키마 단위로 떠서, 1개만 복원 |
| **투명성** | `.dat` 를 열어 내용 그대로 확인·검증 |
| **폐쇄망 배포** | 이미지 하나 + 번들 하나, 대상 서버에 설치 0 (`docker`/`podman`) |
| **속도** | 적응형 병렬 덤프·복원(자동), 거대 테이블 행 샤딩 |
| **전송 효율** | `--compress`(gzip) — 전송/보관 용량 대폭↓, COPY 가 직접 읽어 무손실 |
| **운영 편의** | 진행률 바, 멱등 DDL, 프로시저 자동 포함, 무손실 escape |

## 동작 원리

```
백업:  vertica-python ──SELECT──▶ 값 escape ──▶ <schema>.<table>.dat
       EXPORT_OBJECTS ──▶ schema.ddl.sql (+ 매칭 프로시저, 멱등형)
복원:  vsql ──COPY ... FROM LOCAL──▶ Vertica
```

- **`.dat`** — Vertica `COPY` 기본 컨벤션(파이프 구분, `\N` NULL, 백슬래시 escape) 그대로 →
  가장 빠른 재적재. 줄바꿈·탭·특수문자 **무손실** 라운드트립.
- **적응형 병렬** — 워크로드를 보고 자동 결정: 자잘하면 순차, 테이블 많으면 테이블 병렬,
  거대 테이블은 행 단위 샤딩. **덤프·복원 양쪽** 병렬. 워커 `min(코어, 4)`(`V_DUMP_JOBS` 로 조절).
- **압축**(`--compress`) — `.dat` 를 gzip 으로. 에어갭 전송 짐을 줄이고, 복원은 `COPY ... GZIP`
  으로 압축 파일을 직접 읽어 **무손실**.
- **멱등 DDL** — `CREATE ... IF NOT EXISTS` / `OR REPLACE` 라 재실행해도 안전.

## 빠른 시작

```bash
# [빌드 머신, 인터넷 O] 한 번에 패키징
./docker/package.sh                  # → v_dump-deploy.tar.gz (이미지+래퍼+yaml+로더)

# [대상 호스트, 폐쇄망] 풀고 로드 후 바로 사용
tar xzf v_dump-deploy.tar.gz && cd v_dump-deploy
./LOAD-ME.sh
./v_dump-docker.sh dump --schema YOUR_SCHEMA               # 백업
./v_dump-docker.sh restore YOUR_SCHEMA/all --with-ddl      # 복원
```

> 설치·빌드·접속설정·백업/복원·운영 시나리오·트러블슈팅 **전체 흐름은 [`GUIDE.md`](GUIDE.md)** 를 본다.

## 한계 (정직하게)

- **시점 정합성** — 테이블을 따로 읽으므로, 덤프 중 데이터가 바뀌면 테이블 간 불일치 가능
  (vbr 의 에폭 스냅샷과 다름).
- **규모** — 모든 행을 단일 클라이언트로 당기는 구조라, 초대용량 풀DB 에는 근본적으로 느리다.
  그 영역은 vbr / `EXPORT TO` 가 맞다.
- **증분 없음** — 매 백업이 전량 추출.

> 서버/컨테이너 파일 접근이 확보되면 `EXPORT TO DELIMITED` 기반 고속 경로로 확장할 수 있다
> (논리추출의 천장을 우회). 현재는 "5433 클라이언트 접근만" 전제의 최적 구성이다.
